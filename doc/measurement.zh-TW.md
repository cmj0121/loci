# 量測 Loci

[English](measurement.md) | 繁體中文

Loci 有兩個承諾：夠快、不擋路；以及讓 agent 用更少的 token 找到程式碼。本文件說明這兩件事各要怎麼量測。
被量測的行為定義在[規格](spec.zh-TW.md)裡。

這兩種量測都可以在 Loci 還不存在時先做，用現有的 index 工具代替它。這是確認這個想法划不划算最便宜的方法。

## 1. 速度

### 量什麼

| 指標      | 意思                                    | 怎麼量                                             |
| --------- | --------------------------------------- | -------------------------------------------------- |
| Hook 負擔 | hook 讓 `git commit` 多花的時間         | 同一個 commit，裝與不裝 hook 各跑多次，取差值      |
| 建立時間  | 從 hook 觸發到記憶發布完成              | 由 Loci 記錄的兩個時間點                           |
| 過時視窗  | commit 之後，查詢還拿到舊記憶的時間長度 | 該 commit 的建立時間，看最差情況而不是平均         |
| 查詢延遲  | 從送出 MCP 呼叫到拿到答案               | 每個工具各呼叫數百次；看 p50 與 p95                |
| 切換時間  | `checkout` 之後多久能回答新的 revision  | 在兩個已建好的 branch 之間來回切換                 |
| 儲存空間  | 一個 repository 的記憶占用的磁碟空間    | 每 1,000 個檔案的大小，以及每 100 個 commit 的成長 |

建立時間要分開報告兩種：repository 第一次的完整建立，以及單一 commit 的建立。

### 怎麼執行

- **三種規模的 repository**——小、中、大——讓數字能看出每個指標如何成長。
- **真實的歷史。** 重播每個 repository 最近的 N 個 commit，而不是人造的 commit，變動的大小與樣貌才真實。
- **重複執行並報告分布。** 每個指標取多次執行的中位數，並附上最差情況。
- **同一台機器，並且寫明。** 結果要註明是在哪台機器上取得的；不同機器的數字不互相比較。

## 2. Token 用量

Token 用量無法只量 Loci 本身。它是「agent 搭配 Loci」與「同一個 agent 不用 Loci」在同一組題目上的差距。

### 題目

在一個真實的 repository 上定出一份固定的題目清單。每一題在執行之前就先決定好標準答案——檔案與行數範圍。
清單涵蓋三類：

| 類別             | 例子                                   | 測試的對象   |
| ---------------- | -------------------------------------- | ------------ |
| 知道名稱的查找   | 「`parse_config` 定義在哪裡？」        | symbols      |
| 不知道名稱的查找 | 「失敗的 request 在哪裡重試？」        | notes 與搜尋 |
| 概念問題         | 「這個 function 為什麼要先複製輸入？」 | notes        |

知道名稱的查找本來就是全文搜尋的強項。只由這類題目組成的清單說明不了什麼，所以三類要分開報告。

### 對照組

同一個 model、同一段 prompt，在每種條件下跑完每一題。

| 組別 | 條件                        | 回答的問題         |
| ---- | --------------------------- | ------------------ |
| A    | 只有全文搜尋與讀檔          | 基準               |
| B    | Loci，只有 symbols          | index 省了多少     |
| C    | Loci，symbols 與 notes 都有 | notes 額外省了多少 |

Agent 每次的行為都不一樣，所以每一題在每一組至少執行三到五次。

### 每次執行要記錄的內容

- **Token**——input 與 output 分開，cache 命中的 input 另外列出。以 headless 模式執行 agent 並輸出 JSON，
  就能取得每次執行的 usage。
- **Tool call 次數與總時間。**
- **正確性**——答案是否命中標準答案的檔案與行數範圍。
- **採用率**——agent 是先問 Loci，還是照樣去做全文搜尋。

### 必須算進去的成本

- **固定成本。** MCP 工具的定義與 skill 的文字，每個 session 都要付一次，要算進 B 組與 C 組。
- **撰寫 note。** Notes 是 LLM 寫的，本身要花 token。回本點是「寫 note 花掉的 token」除以
  「每次查詢省下的 token」：也就是查詢幾次之後，notes 才算回本。
- **誠實的基準。** A 組要讓 agent 照平常的方式使用全文搜尋。拿「讀整個檔案」當基準，會讓所有的節省都虛高。

### 報告什麼

最主要的數字是**每答對一題花費的 token**，依題目類別與組別分開。Token 變少但答錯變多，不算節省。

另外附上：

- 每題 token 的中位數與分布；
- 各組的答對比例；
- B 組與 C 組的採用率；
- notes 的回本點。

## 3. 解讀結果

| 結果                                       | 代表的意思                           |
| ------------------------------------------ | ------------------------------------ |
| B 在不知道名稱的查找上贏 A，知道名稱的沒有 | 符合預期；index 的價值在困難的問題上 |
| C 要查詢很多次之後才贏 B                   | notes 在常被閱讀的程式碼上才划算     |
| 採用率低                                   | 需要改進的是 skill，而不是 index     |
| 在 prompt 上感覺得到 hook 的負擔           | 違反了原則：Loci 擋路了              |
| A 在每一類都跟 B、C 一樣好                 | 這個想法在這個 repository 上不划算   |
