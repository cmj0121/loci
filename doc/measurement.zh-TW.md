# 量測 Loci

[English](measurement.md) | 繁體中文

Loci 有兩個承諾：不擋路；以及讓 agent 用更少的 token 找到程式碼。本文件說明這兩件事怎麼量測，
以及第一次量測的發現。被量測的行為定義在[規格](spec.zh-TW.md)裡。

這兩種量測都可以在 Loci 還不存在時先做，用現有的 index 工具代替它。這是確認這個想法划不划算最便宜的方法。

## 1. 速度

**目的：** 證明 Loci 不會讓開發者等待。

| 指標      | 意思                                    | 怎麼量                                             |
| --------- | --------------------------------------- | -------------------------------------------------- |
| Hook 負擔 | hook 讓 `git commit` 多花的時間         | 同一個 commit，裝與不裝 hook 各跑多次，取差值      |
| 建立時間  | 從 hook 觸發到記憶發布完成              | 由 Loci 記錄的兩個時間點                           |
| 過時視窗  | commit 之後，查詢還拿到舊記憶的時間長度 | 該 commit 的建立時間，看最差情況而不是平均         |
| 查詢延遲  | 從送出 MCP 呼叫到拿到答案               | 每個工具各呼叫數百次；看 p50 與 p95                |
| 切換時間  | `checkout` 之後多久能回答新的 revision  | 在兩個已建好的 branch 之間來回切換                 |
| 儲存空間  | 一個 repository 的記憶占用的磁碟空間    | 每 1,000 個檔案的大小，以及每 100 個 commit 的成長 |

建立時間分開報告：第一次完整建立，以及單一 commit 的建立。

**做法：** 在小、中、大三個 repository 上重播真實的最近 N 個 commit。報告多次執行的中位數並附上最差情況，
在同一台寫明的機器上取得。

**判定：** 開發者在 prompt 上感覺得到 hook 的負擔，就違反了原則：Loci 擋路了。

## 2. Token 用量

**目的：** 看 agent 搭配 Loci，是否比同一個 agent 不用 Loci 在同一組題目上花更少的 token。

**題目。** 在真實的 repository 上定出固定的清單，每題在執行前就決定好標準答案（檔案與行數範圍）。
三類分開報告：

| 類別             | 例子                                   | 測試的對象   |
| ---------------- | -------------------------------------- | ------------ |
| 知道名稱的查找   | 「`parse_config` 定義在哪裡？」        | symbols      |
| 不知道名稱的查找 | 「失敗的 request 在哪裡重試？」        | notes 與搜尋 |
| 概念問題         | 「這個 function 為什麼要先複製輸入？」 | notes        |

不知道名稱的查找與概念問題，不能帶有只有答案程式碼才有的字：每個字用 `rg` 檢查，只命中答案就改寫題目。
清單要在不只一種規模的 repository 上執行。

**對照組。** 每一組都是同一份記憶的一種介面，用同一個 model 與同一段 prompt。

| 組別 | 介面               | Agent 有什麼                              | 回答的問題               |
| ---- | ------------------ | ----------------------------------------- | ------------------------ |
| A    | 只有全文搜尋       | 全文搜尋與讀檔                            | 基準                     |
| B    | MCP                | Loci 的 symbol 工具與 skill               | index 省了多少           |
| C    | MCP                | Loci 全部工具、skill 與 notes             | notes 額外省了多少       |
| D    | skill + CLI        | `loci` CLI、它的 skill 與 notes；沒有 MCP | CLI 能否避開 MCP 的成本  |
| E    | skill + CLI + hook | D 再加上一個會注入建議的 prompt hook      | 主動送上的建議有沒有幫助 |
| E0   | skill + CLI + hook | E 但沒有 notes：CLI 與 hook 只比對名稱    | notes 為 E 多帶來什麼    |

**執行。** 每題在每一組跑 5 次，交錯進行（A、E、E0、A、E、E0、...），漂移才會平均落在每一組上。
每次執行都有新的 `git worktree`、空的 agent 設定與重新複製的 notes。答案、使用者的 MCP server、plugin、
編輯、上網與 subagent 都碰不到。

**算什麼。** 每次執行記錄：input、output 與 cache 的 token、成本、tool call 次數、總時間、正確性，
以及採用率（第一個定位用的呼叫是不是 Loci）。每一組都要算自己的固定成本（工具定義、skill 文字），
MCP 組還要算 ToolSearch 載入工具的那一輪。寫 notes 也要算：回本點是寫 notes 花的 token 除以每次查詢省下的 token。
A 組照 agent 平常的方式使用全文搜尋。

**判定。** 主要數字是**每答對一題花費的 token**，依類別與組別分開，旁邊附上**每次執行的成本**，
因為便宜的 cache 讀取可能讓 token 的節省在成本上消失。每個組別 − A 的差距都附上 bootstrap 95% CI，
在每一題內對執行重新抽樣；CI 包含 0 就不算結果。規則在執行之前寫下來。

## 3. Gate 0 結果

- Gate 0 的規則（在不知道名稱的查找上贏過全文搜尋）五輪都沒有達到。Loci 當作更快找到程式碼的方法並不划算：
  不論 53k 行還是 596k 行，全文搜尋 1–2 次呼叫就找得到 function。
- 划算的是用 prompt hook 把 notes 交給 agent 回答概念問題。r5 在 ripgrep 上，E 每答對一題省 16,157 token、
  每次執行省 $0.0020，兩個 CI 都不包含 0，答對率 77% 對 70%。沒有 notes（E0）就沒有明確的收益。
- MCP 不適合：在 Claude Code 裡它的工具藏在 ToolSearch 後面，多出來的那一輪花的比工具省的還多。
- 還沒解決的成本是 note pass：ripgrep 要 $13.77，約 6,900 題概念問題才回本，所以 notes 要在需要時才寫。
  還沒證明：大 repository 加上 notes，以及真正的 Loci——每一輪用的都是替身。
- 所以 [MVP 改成](#mvp-的改變) prompt hook 加 CLI 的 context provider，notes 需要時才寫，不用 MCP。

Loci 的 Python 替身跑了五輪，每一組都用 Sonnet 5.5。完整的報告就是證據：

- r1，A、B、C 組：[`results/gate0-r1.md`](results/gate0-r1.md)；
- r2（B、C 重跑）與 r3（D、E），A 沿用 r1：[`results/gate0-r2-r3.md`](results/gate0-r2-r3.md)；
- r4，交錯執行，每題 5 次，附 CI：[`results/gate0-r4.md`](results/gate0-r4.md)；
- r5，只考概念問題，也檢查理由：[`results/gate0-r5.md`](results/gate0-r5.md)。

### 題目缺陷

有四題在每一組幾乎每次都錯：ripgrep 三題、rust-analyzer 一題。agent 找到了正確的檔案，卻指向相鄰的
function，或沒有用到要求的說法。缺陷在題目，不在組別。改用檔案層級計分，順序不變：ripgrep 每答對一題 token
為 A 75,509、E 62,044、E0 70,395；rust-analyzer 為 A 77,360、E0 71,100。每次成本與計分方式無關。

### Note pass

替 ripgrep 寫 notes 花了 2 個 session、約 53M token（52,969,105）與 $13.77，涵蓋 2,165 個非測試 function
中的 2,090 個。以 B 為比較對象，要 6,203 次（r1）或 8,721 次（r2）查詢才回本。以 A 為比較對象，
照 E 在 r5 每題概念問題省 $0.0020 計算，要約 6,900 題。

### 採用率

在 r3，agent 先呼叫 `loci` 的比例是 14%（E）與 22%（D）。在 r4，ripgrep 上 E 是 22%、E0 是 35%，
rust-analyzer 上 E0 是 20%。r4 的數字取自原始執行紀錄；`results/gate0-r4.md` 沒有列出採用率。

### MVP 的改變

| 原本                         | 改成                                                 |
| ---------------------------- | ---------------------------------------------------- |
| 六個 MCP 工具                | prompt hook 加 CLI；不用 MCP                         |
| 找程式碼的 symbol 搜尋       | 解釋程式碼的 context provider                        |
| 事先替每個 function 寫 notes | 需要時才寫：被問到或最近改過的 function              |
| 每個 repository 行為相同     | 小的只在背景建 DB（passive），大的主動提供（active） |
